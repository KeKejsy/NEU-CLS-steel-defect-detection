# C 部分交付说明：钢材表面缺陷检测与定位（任务2）

负责人：C（检测模型负责人）　｜　框架：PaddlePaddle（原生手写，未用 PaddleDetection）｜　完成日期：2026-09-14

## 摘要

- **两个单阶段检测网络（YOLOv3 / PP-YOLOE-s）均已按配置跑满训练，但验证 mAP@0.5 ≈ 0.0000~0.0007，判定为失败。**
  框的定位是准的（GT 所属特征点上框 IoU 达 0.742/0.757），但**置信度分支学不出来**：正样本每图仅 2~3 个，
  候选位置在 10⁴ 量级，占比 0.3%，正确框的 obj 分数只有 0.056、在 307 个候选中排第 135 位，被 top_k 截断。
  已排除"训练不充分""小目标难检""排序方式不对"等解释，详见 4.2 节。
- 改用的方案是**多尺度多长宽比滑窗 → 区域验证器（判类）+ 区域精修器（判类 + 框回归）→ 概率几何平均融合 → NMS**，
  最终 **测试集 mAP@0.5 = 0.1552、召回 0.6483、精确率 0.0782**（每图输出 19.5 框，真值平均 2.4 框）。
- **客观结论：任务2 属于部分达标。** 召回率（0.65）与各类定位可用，但精确率过低（0.078）导致 mAP 只有 0.155，
  未达到常规检测任务 mAP@0.5 ≥ 0.5 的水平。**这个结论如实写在文档里，报告中请勿美化。**
- 交付的三个可用模型：区域验证器（GT 框上分类准确率 97.00%）、区域精修器（精修后平均 IoU 0.442），
  以及两套完整可实现、可训练、可评估、可可视化的单阶段检测代码（作为对照基线）。

## 二、技术路线：为什么不用 PaddleDetection

原计划用 PaddleDetection，动手前实测了可行性，结论是**不能用**：

| 检查项 | 实测结果 |
|---|---|
| `PaddleDetection/requirements.txt` 第 1 行 | `numpy < 2.0`，而本机 numpy 是 **2.5.2** |
| `git clone` release/2.9 后 `import ppdet` | 逐层失败：缺 `pycocotools` → `requests` → `imgaug.augmentables` → … |
| 需要的额外依赖 | 约 15 个，且必须把 numpy 降到 < 2 |

降级 numpy 会连带搞崩成员 A 已跑通的数据脚本（项目铁律明令避免）。

实测 `paddle.vision.ops` 已自带检测所需的全部算子：

```
deform_conv2d   nms（原生支持 category_idxs 分类批量 NMS）   yolo_box
matrix_nms      roi_align      prior_box      yolo_loss
generate_proposals      distribute_fpn_proposals      psroi_pool
```

**最终方案：用原生 Paddle 手写两个检测网络，零新增依赖、不编译自定义 OP。**

## 三、实验设置

**数据**（由 A 提供，只读不改）：1260 / 270 / 270，种子 2026，分层划分。训练脚本只读 train/val，
测试集仅用于最终评估一次。

**评估口径**：VOC 口径 mAP@0.5，每类按分数降序匹配、101 点插值、6 类 AP 算术平均。
坐标全流程用归一化 xyxy 落在 [0,1]，评估阶段无需坐标反变换。
mAP 实现经 **6 项已知答案单元测试**校对（完美预测=1.0；框微抖但仍 IoU>0.5=1.0；完全错位=0.0668；
类别全错=0.0；只命中一半=0.5944；PR 曲线 recall 单调不减），全部符合预期。

**两个网络的设计对比**（对比的意义在于检验 anchor-based 与 anchor-free 在极端宽高比数据上的差异）：

| | YOLOv3 | PP-YOLOE-s |
|---|---|---|
| 主干 | Darknet53（残差瓶颈 ×26） | CSPResNet（CSP + RepConv + ESE 注意力） |
| 颈部 | FPN 自顶向下三层融合 | CSPPAN 双向融合四层 |
| 检测方式 | anchor-based，9 个预设 anchor | anchor-free，每个特征点直接回归 |
| 框回归 | 直接回归 + GIoU 损失 | DFL 分布式回归 + GIoU |
| 置信度 | obj × cls（两个分支） | 类别分数即置信度（无 obj 分支） |
| 参数量 | 6440.10 万 | 2375.17 万 |
| 输入尺寸 | 416 | 640 |

**运行环境**：PaddlePaddle-GPU 3.2.0 + RTX 5070 Ti Laptop 12GB（sm_120），Python 3.12.13。
> 注意：C 的机器与 README 记载的 CPU 环境**不是同一台**。代码只依赖 numpy / paddle / PIL / matplotlib / yaml，
> 与 CPU 环境兼容，但训练在纯 CPU 上不现实（滑窗方案的评估也需 ~3.4 秒/图）。

**显存红线（实测踩过）**：PP-YOLOE-s 在 640 输入下 batch 必须 ≤ 8。
bs=16 时峰值显存 12.18GB 顶满 12GB，触发显存重试，单步从 249ms 暴涨到 **52 秒（慢 200 倍）**。
更隐蔽的是：**两个训练进程并发同样会触发**，PP-YOLOE-s 单 epoch 从 51 秒涨到 7224 秒（慢 134 倍）。
所以两个网络必须串行训练。

## 四、结果

### 4.1 单阶段检测：失败

| 网络 | 输入 | epoch | 参数量(万) | 最佳验证 mAP@0.5 | 耗时 |
|---|---|---|---|---|---|
| YOLOv3 | 416 | 120 | 6440.10 | **0.0000** | 40.2 分钟 |
| PP-YOLOE-s | 640 | 100 | 2375.17 | **0.0000** | 85.8 分钟 |

跑满训练后相较调试期（只跑 40/17 epoch）**没有实质改善**（0.0000 → 0.0007），
这条证据排除了"训练不充分"。

### 4.2 单阶段为什么失败（本次工作最有价值的部分）

| 检查项 | 实测 | 说明 |
|---|---|---|
| GT 所属特征点上的框 IoU | **0.742 / 0.757** | 定位没问题 |
| 同一框的 obj 分数 | 0.056 | 在 307 个候选中排**第 135 位** |
| 结果 | mAP@0.5 = 0 | 被 top_k 截断淘汰 |
| 根因 | 正样本 2~3 个/图 vs 候选位置 10⁴ 量级（0.3%） | 置信度分支的类别极度不平衡 |

已尝试并**排除**的方案（都有实测数据支撑）：

| 尝试 | 结果 |
|---|---|
| 改置信度排序：obj×cls / 纯 cls / 纯 obj / obj×cls² | mAP 全部为 0 |
| 提高 top_k：100 → 300 → 1000 | 0.0002 → 0.0025 → 0.0025（触顶） |
| 用边缘能量（梯度幅值）当分数 | 0（该数据集背景纹理本身很重，边缘不是有效线索） |
| obj 分支偏置初始化 -4.5 / -2.0 / 0 | 无实质改善 |
| obj 损失改为正负样本各自归一化 | 无实质改善 |
| k-means 定制 anchor（IoU 0.567 → 0.692） | 定位略好，mAP 仍为 0 |
| 统一训练/验证输入尺度（原来随机缩放不一致） | 修正了一个真 bug，但 mAP 仍为 0 |
| 双阶段：检测器候选 + 验证器重打分 | 仍为 0，正确框排 135 位被截断 |
| 按目标尺寸分档评估 | 大/中/小框 mAP **全部为 0** —— 排除"小目标难检" |
| 训练轮数翻 3 倍 | 0.0000 → 0.0007 —— 排除"训练不充分" |

**根因**：单阶段置信度分支本质是"在 10⁴ 量级候选里做二分类、正样本只有 2~3 个"。
本数据集只有 1800 张图、平均每图 2.3 个框，正样本绝对数量太少，网络学不出"这个位置的框好不好"。
它能把框回归准（稠密监督），但学不出可靠置信度（极端不平衡的稀疏监督）。

这也解释了滑窗方案为什么能工作：它把同一件事变成了**稠密监督的分类任务**。

### 4.3 最终方案：滑窗 + 验证器/精修器融合

迭代历程：

| 方案 | 验证集 mAP@0.5 | 测试集 mAP@0.5 | 说明 |
|---|---|---|---|
| 初版：滑窗 + 验证器 | 0.0677 | 0.0548 | 只用验证器判类 |
| 第二轮：+ 精修器 + 概率融合 | 0.1575 | 0.1435 | 新增框回归与融合 |
| 第三轮：+ 窄宽高比滑窗 | 0.1675 | — | 针对细长缺陷 In / Sc |
| **★完整流水线重跑（最终交付）** | **0.1681** | **0.1552** | 一键复现，186.2 分钟 |
| 累计提升 | **+148%** | **+183%** | — |

最终指标（完整流水线重跑）：

| 划分 | mAP@0.5 | 精确率 | 召回率 | 每图框数 |
|---|---|---|---|---|
| 验证集 270 张 | 0.1681 | 0.0755 | 0.6307 | 19.8 |
| **测试集 270 张** | **0.1552** | **0.0782** | **0.6483** | 19.5 |

测试集每类 AP@0.5：

| 类别 | Cr 龟裂 | In 夹杂 | Pa 斑块 | PS 麻点 | RS 氧化铁皮压入 | Sc 划痕 |
|---|---|---|---|---|---|---|
| AP | 0.1361 | 0.0590 | 0.2011 | **0.3533** | 0.1120 | 0.0701 |
| 召回 | 0.6990 | 0.4839 | 0.7077 | **0.7857** | 0.7222 | 0.6047 |

PS 麻点与 Pa 斑块表现最好；In 夹杂与 Sc 划痕最差（细长形状，滑窗难以贴合）。

第二阶段两个模型：

| 指标 | 区域验证器 | 区域精修器 |
|---|---|---|
| 任务 | 判类（7 类） | 判类 + 框回归 |
| 参数量 | 258.67 万 | 259.08 万 |
| 整体准确率 | 88.72% | 78.07% |
| **真实候选分布上的判类准确率** | 95.92% | 96.43% |
| 精修后平均 IoU | — | 0.4442 |
| GT 框上的分类准确率（测试集） | **97.00%** | — |

精修器整体准确率低于验证器，因为它的训练集更难（含大量"部分覆盖缺陷"的模拟候选），
但在真实候选分布上判类反而略优（96.43% vs 95.92%）——**这正是融合能奏效的原因**。

### 4.4 消融实验（验证集 270 张，同批数据同后处理）

| 配置 | mAP@0.5 |
|---|---|
| 滑窗 + 验证器（只判类） | 0.1231 |
| 滑窗 + 精修器（只用一个模型） | 0.0886 |
| **滑窗 + 两者融合（第二轮）** | **0.1575** |
| **再加窄宽高比滑窗（第三轮，最终）** | **0.1675** |

后处理最优参数：滑窗步长 12、宽高比 0.35/0.6/1.0/1.7、分数阈值 0.6、
NMS IoU 0.4（比常规 0.5 更严，因为每图几十框而真值只有 2.4 个）、
先截 top_k=150 再 NMS（避免低分框把高分框误压掉）、max_det=50。

## 五、已验证有效 / 无效的设计

**有效（有数据支撑）**：
1. 验证器 + 精修器**概率几何平均融合** —— 决定最终 mAP 的核心
2. 精修器做**框回归**（消融：0.0991 vs 仅分类 0.0406）
3. 滑窗长宽比下探到 **0.35**（Sc 0.0916→0.1372，RS 0.1221→0.1563）
4. NMS IoU 0.4；先按分数截 top_k 再 NMS；最多 50 框/图

**已验证无效并放弃（同样有数据支撑）**：
- 精修器抖动范围放宽（0.2385 → 0.1289）
- 验证器加困难负样本 / 膨胀 GT（0.2275 → 0.1857）
- 滑窗最大尺度提到 0.9（0.2369 → 0.2061）
- 迭代式二轮精修（二轮反而破坏已定位好的框，Sc 0.281 → 0.098）
- 限制输出框数量

**规律**：本方案的两个判别模型与滑窗配置已处于"互相配合"的状态，
单独加强任何一个环节都会破坏平衡。再提升需要换层次，不是继续微调。

## 六、踩坑记录（对报告「遇到的问题与解决」一节有用）

1. **`masked_select` 反向慢 1600 倍** —— 改为「全量算损失 + 掩码加权归约」后单步从 3927ms 降到 249ms。
2. **IoU 损失误用两两矩阵导致爆显存** —— (B,N,4) 且 N=68000 时矩阵元素上亿，申请 34.45GB 直接 OOM。
   IoU 损失是一一对应关系，逐元素直算即可。
3. **退化框污染 mAP** —— 四坐标各自 clip 会把部分出界的框压成零宽零高，
   零面积框在 NMS 里被当作互不重叠而全部留下（27000 个框里 4082 个退化框）。改为「先夹中心点与宽高，再由中心重构四角」后降为 0 个。
4. **非二次幂输入尺寸让 FPN 相加报错** —— 200×200 时特征是 25/13/7，硬写 `scale_factor=2` 会 Broadcast 报错。
   改为按目标特征图尺寸 `interpolate(size=[h,w])`。
5. **损失归一化口径写错导致训练发散** —— obj 分支按「正样本数」归一化，损失被放大到 44636、梯度范数 2.4e6。
   正确做法是按全部元素取平均。
6. **学习率 warmup 形同虚设** —— 自写 `LambdaDecay` 闭包时 lr 只升到预期的 1/30。改用原生 `LinearWarmup + CosineAnnealingDecay`。
7. **主干结构连写错三次** —— Darknet53 的 stem 下采样次数、阶段通道数、取哪三层输出各错一次。
   教训：有固定官方层序的结构应逐层写死并与官方表对照，不要靠循环推导。
8. **子集抽样偏置导致超参扫错** —— 直接用 `ds.samples[:N]` 取前 80 张，划分文件按类别前缀排序，
   前 80 张只有 Cr 和 In 两类，扫出的 mAP（0.043）与全量（0.099）差一倍多。
   后写 `tools/sweep_refine.py` 做分层抽样才可靠。

## 七、结论与不足

**拿到了什么**：
- 一套可用的端到端检测流程（滑窗 + 双模型融合），测试集 mAP@0.5 = 0.1552、召回 0.6483；
- 两个可靠的缺陷区域判别模型（GT 框上分类准确率 97.00%，精修后平均 IoU 0.442）；
- 两套原生 Paddle 实现的单阶段检测网络（含训练/评估/可视化全套脚本），零新增依赖；
- 一套可复用的诊断工具链（16 个脚本），本轮迭代方向靠它定位而非试错。

**不足（如实列出）**：
1. **精确率过低（0.0782）**：每图输出 19.5 框而真值只有 2.4 个，误检居多。mAP@0.5 = 0.155 未达常规及格线。
2. **单阶段检测器完全未起来**：两个网络 mAP≈0，只能作为失败基线保留。
3. **细长缺陷仍差**：In 夹杂 AP 0.059、Sc 划痕 0.070，滑窗形状与细长目标匹配度不够。
4. **速度慢**：融合方案约 3.4 秒/图（CPU 上更慢），离实用有距离。
5. **未用预训练主干**：受 PaddleDetection 的 numpy<2 依赖限制，主干从零训练，小数据集上吃亏明显。

**下一步改进建议**：
1. 给置信度分支加 **Focal Loss 或 OHEM**（只回传损失最大的若干负样本），而不是简单调 `pos_weight`；
2. 换用**有预训练权重**的主干，对小数据集帮助会很大；
3. 在滑窗基础上加一个**框回归头**（类似 RPN 的 refine），把 IoU 从 0.507 提到 0.6+ 应能显著改善 mAP@0.5；
4. 数据层面：把 200×200 原图做**重叠裁块**扩充训练样本，缓解正样本过少。
