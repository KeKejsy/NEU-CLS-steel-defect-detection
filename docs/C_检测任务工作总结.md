## 二、最重要的一个方案调整：没有使用 PaddleDetection

原计划按 README 用 PaddleDetection（PP-YOLOE-s + YOLOv3）。**动手前实测发现不能用**：

| 检查项 | 实测结果 |
|---|---|
| `PaddleDetection/requirements.txt` 第 1 行 | `numpy < 2.0`，而本机是 **numpy 2.5.2** |
| `git clone` release/2.9 后 `import ppdet` | 逐层失败：缺 `pycocotools` → `requests` → `imgaug.augmentables` → … |
| 需要的额外依赖 | 约 15 个，且**必须把 numpy 降到 <2** |

降 numpy 会连带破坏成员 A 已完成的数据脚本，这是项目铁律明确要避免的事。
更关键的是**没必要**——实测 `paddle.vision.ops` 原生自带检测所需的全部算子：

```
deform_conv2d   nms（原生支持 category_idxs 分类批量 NMS）   yolo_box
matrix_nms      roi_align      prior_box      yolo_loss
generate_proposals      distribute_fpn_proposals      psroi_pool
```

**最终方案：用原生 Paddle 手写两个检测网络，零新增依赖、不编译自定义 OP。**
这也符合项目既有风格（README 给成员 B 的建议同样是「自己写训练循环，别折腾框架源码」）。

**实测训练速度**（有 GPU，比 README 记载的 CPU 数据快约 30 倍）：

| 网络 | 输入 | batch | 单步 | 每 epoch | 峰值显存 |
|---|---|---|---|---|---|
| YOLOv3 | 416 | 16 | 181 ms | 约 19 s | 3.17 GB |
| PP-YOLOE-s | 640 | 8 | 249 ms | 约 50 s | 9.7 GB |
| PP-YOLOE-s | 640 | 16 | **51984 ms** | 不可用 | 12.18 GB（顶满） |

> ⚠️ **显存红线**：PP-YOLOE-s 在 640 输入下 batch **必须 ≤ 8**。
> bs=16 时峰值显存顶满 12GB，触发显存重试，单步从 249ms 暴涨到 52 秒（慢 200 倍）。
> 这不是报错，是静默变慢，很容易被误判成"模型太大跑不动"。
>
> 另一个同类陷阱：**两个训练进程并发跑也会触发显存重试**。
> 实测 PP-YOLOE-s 在另一进程同时训练时，单 epoch 从 54 秒暴涨到 7224 秒（慢 134 倍）。
> 所以两个网络必须**串行训练**——这也是 README「CPU 训练实操建议」里
> 「两个网络串行训，不要同时开」的同一个道理，只是原因从 CPU 核数变成了显存。

**两个网络的跑满训练结果**（均已按配置跑满，非调试期的截断训练）：

| 网络 | epoch | 参数量(万) | 最佳验证 mAP@0.5 | 训练耗时 |
|---|---|---|---|---|
| YOLOv3 | **120（跑满）** | 6440.10 | **0.0007** | 38.0 分钟（19.0 s/epoch） |
| PP-YOLOE-s | **100（跑满）** | 2375.17 | **0.0000** | 81.9 分钟（49.2 s/epoch） |

> 此前调试期只跑了 40 / 17 epoch，本次已重跑至配置上限。**结论没有改变**：
> YOLOv3 从 0.0000 升到 0.0007，PP-YOLOE-s 仍为 0.0000。
> 这从实验上确认了 §8.2 的判断 —— **mAP 偏低的原因不是训练轮数不够**，
> 而是置信度分支在正样本占比 0.3% 的极端不平衡下学不出判别力。
> 训练轮数翻三倍只换来 0.0007 的提升，这条线索可以排除了。

anchor-based 方法需要预设宽高比，而 anchor-free + DFL 不依赖先验宽高，
理论上更适合。实验就是为了检验这一点。

### 6.0 迭代历程与最终结果（**核心结论**）

检测效果经过**两轮**迭代后大幅提升：

| 方案 | 验证集 mAP@0.5 | 测试集 mAP@0.5 | 关键改动 |
|---|---|---|---|
| 初版：滑窗 + 验证器 | 0.0709 | 0.0548 | 只用验证器判类 |
| 第二轮：+ 精修器 + 概率融合 | 0.1575 | **0.1435** | 新增框回归 + 双模型融合 |
| **第三轮：+ 窄宽高比滑窗** | **0.1675** | 未重跑 | 针对细长缺陷 In/Sc |
| **累计提升（验证集）** | **+136%** | — | 0.0709 → 0.1675 |

> **关于测试集**：第三轮只在**验证集**上做确认（0.1575 → 0.1675），未重跑测试集，
> 因此测试集口径的最终数字仍为 **0.1435**（第二轮配置）。
> 重跑命令见 `src/det/README_det.md` 第 9.1 节。

每类 AP@0.5（第二轮配置，测试集）：

| 类别 | Cr 龟裂 | In 夹杂 | Pa 斑块 | PS 麻点 | RS 氧化铁皮压入 | Sc 划痕 |
|---|---|---|---|---|---|---|
| AP | 0.125 | 0.050 | **0.214** | **0.278** | 0.150 | 0.043 |
| 召回 | 0.709 | 0.490 | 0.777 | **0.800** | 0.722 | 0.512 |

**验证集上三轮的每类 AP 对比**（第三轮的收益集中在细长缺陷）：

| 类别 | 初版 | 第二轮 | 第三轮 | 累计 |
|---|---|---|---|---|
| Cr 龟裂 | 0.090 | 0.126 | 0.120 | +33% |
| In 夹杂 | 0.013 | 0.087 | 0.075 | +478% |
| Pa 斑块 | 0.120 | 0.244 | 0.240 | +100% |
| PS 麻点 | 0.086 | 0.275 | 0.277 | +222% |
| RS 氧化铁皮压入 | 0.116 | 0.122 | **0.156** | +35% |
| Sc 划痕 | 0.000 | 0.092 | **0.137** | 从 0 起步 |
| **总体** | **0.0709** | **0.1575** | **0.1675** | **+136%** |

**第三轮的发现过程**：

1. 写 `tools/analyze_result.py` 拆解混淆矩阵，得到关键事实：**错分列全为 0** ——
   模型从不把缺陷判成别的类别，所有误差只有「误检」与「漏检（IoU 不够）」两种；
2. 漏检集中在 `In 夹杂`（召回 0.49）与 `Sc 划痕`（0.51），其余四类 0.71~0.80；
3. 统计各类框形状后发现根因：In 的宽高比是 **0.37**、Sc 是 **0.18**，
   而原滑窗宽高比只有 `(0.6, 1.0, 1.7)`，**产生不出这种细长形状的窗口** ——
   候选里根本没有贴合的框，分类器再强也救不回来；
4. 加入 `0.35` 档宽高比后，完整验证集上 **Sc +0.046、RS +0.034**，其他类基本持平，
   总体 mAP **0.1575 → 0.1675（+6.4%）**。A/B 确认实验（120 张分层抽样）显示 +5.1%，
   两个不同样本量下结论一致。

**第三轮还试过一个失败的方向（同样值得记录）**：

从「高分窗口只有 8.3% 与 GT 完全无重叠」这一实测出发，我判断大量误检是「差一点命中」的框，
于是放宽精修器训练时的抖动范围（尺度 0.20~0.65 → 0.18~0.85、中心偏移 ±25% → ±40%）重训 60 epoch，
想让网络多见这类困难样本。**结果反而更差**：同一批图上 mAP 0.2385 → 0.1289。

原因是**抖动范围应与推理分布匹配，而不是越大越好** —— 滑窗实际产生的尺度就是 0.2~0.65，
放宽后合成任务与真实分布脱节。更值得注意的是：训练日志里的「合成 IoU」在放宽后反而更低
（0.336 vs 0.442），只看这个指标会得出完全相反的结论。真正有效的是
**推理分布上的精修增益**，为此专门写了 `tools/compare_refiners.py` 做区分。

> 教训：**合成指标 ≠ 真实收益**。该对比脚本因此保留在 tools/ 里，避免以后再被训练日志误导一次。

**第二轮的发现过程**（比调参本身更有价值）：

1. **先量化诊断，不盲目试错**。写了 `tools/bottleneck.py`，得到三个关键数字：
   - 滑窗候选 2028 个/图，IoU≥0.5 的召回**上限 70.1%** → 说明还有空间，不是定位绝境；
   - 验证器判「是不是缺陷」95.1%、判「是哪一类」97.35% → **判类环节没问题**；
   - **GT 最佳候选的排名中位数 194** → 正确框被海量候选淹没了。
2. **关键一击**：测出「阈值从 0.5 提到 0.9，每图框数只从 49.8 降到 48.6」。
   这说明验证器把几乎所有覆盖缺陷的窗口都判成了缺陷 —— 它训练时只见
   「GT 框 vs 随机背景」，**从未见过推理时的密集重叠窗口**。
3. **方向因此明确**：不是调阈值、不是换聚合，而是**让框变准**。
   新增 `core/refiner.py`：在验证器基础上加**框回归头**，把候选框对齐到真实缺陷。
   消融证明这是主要收益来源：同参数下带框回归 0.0991 vs 关掉 0.0406。
4. **进一步发现概率融合有效**：验证器（分类头训练更充分）与精修器（见过真实候选分布）
   误差互补，几何平均后判类准确率从 95.9%/96.4% 升到 **96.9%**，mAP 再翻近一倍。

**消融实验**（同一批数据、同一后处理，验证集 270 张）：

| 配置 | mAP@0.5 |
|---|---|
| 滑窗 + 验证器（只判类） | 0.1231 |
| 滑窗 + 精修器（只用一个模型） | 0.0886 |
| **滑窗 + 两者融合（第二轮方案）** | **0.1575** |
| **再加窄宽高比滑窗（第三轮方案）** | **0.1675** |

> ⚠️ 一个值得记录的教训：最初我用 `ds.samples[:N]` 取子集扫超参，结论是错的 ——
> 划分文件按类别前缀排序，前 80 张只有 Cr 和 In 两类（45+35），不代表整体，
> 扫出的 mAP（0.043）与全量评估（0.099）差一倍多。
> 后来专门写了 `tools/sweep_refine.py` 做**分层抽样**（每类等量），结论才可靠。

## 七、遇到的问题（按代价排序）

详细技术记录见 `src/det/README_det.md` 第八节。下面按"花了多少时间"排序：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | **单阶段检测器 mAP 恒为 0** | 置信度分支正样本仅占候选位置 0.3%，学不出判别力 | 未根治；改用「滑窗 + 验证器」绕过（详见第七节） |
| 2 | `masked_select` 反向慢 1600 倍 | 8500×68 中间张量展开 + 散射梯度 | 改为「全量算损失 + 掩码加权归约」，提速 **16 倍** |
| 3 | IoU 损失爆显存（申请 34GB） | 误用两两矩阵，而 IoU 损失是一一对应关系 | 改为逐元素直算 |
| 4 | 退化框污染 mAP（4082/27000） | 四个坐标各自 clip 到 [0,1] 把框压成零宽高 | 改为「先夹中心点与宽高，再由中心重构」，退化框归 0 |
| 5 | 学习率 warmup 形同虚设 | 自写 `LambdaDecay` 被 optimizer 二次处理，只升到预期 1/30 | 改用原生 `LinearWarmup + CosineAnnealingDecay` |
| 6 | obj 损失 44636、梯度 2.4e6 | 按正样本数归一化，而负样本上万 | 改为按全部元素取平均 |
| 7 | 训练/验证输入尺度不一致 | 随机缩放后每 batch 尺寸不同，特征图 7×7 vs 13×13 | 统一 padding 到固定边长 |
| 8 | Darknet53 结构连写错 3 次 | 用循环+通道表推导时把 /2 与 /4 位置搞反 | 改为逐层写死并与官方表对照，靠逐层打印形状定位 |
| 9 | FPN 相加报 Broadcast 错 | 200 输入时尺度是 25/13/7，硬写 `scale_factor=2` | 改为按目标尺寸 `interpolate(size=)` |
| 10 | `nms` 报 top_k 断言失败 | 训练早期一张图只有几个框，少于 top_k | 把 top_k 夹到实际框数 |
| 11 | `viz_det.py` PIL 报错 | 极小框转像素后不足 1px | 画图前统一做框合法化 |

## 八、结论与后续建议

### 8.1 拿到了什么

1. **一个可用的端到端检测流程**（滑窗 + 验证器/精修器融合 + 窄宽高比滑窗）：
   **验证集 mAP@0.5 = 0.1675**（比初版 0.0709 提升 **136%**）、
   **测试集 mAP@0.5 = 0.1435、召回 0.655**（比初版 0.0548 提升 **162%**）；
2. **两个可靠的缺陷区域判别模型**：验证器在测试集 GT 框上分类准确率 **97.00%**
   （每类召回 ≥0.94）；精修器在其上再做框回归，精修后平均 IoU 0.442；
3. **两套单阶段检测网络的完整实现**（YOLOv3 / PP-YOLOE-s）+ 训练/评估/可视化/Demo 全套脚本，
   全部基于原生 Paddle，零新增依赖、不编译自定义 OP；
4. **一套可复现的评测与诊断工具链**：mAP 实现经 6 项已知答案单测
   （完美预测=1.0、框微抖=1.0、完全错位=0.0668、类别全错=0.0、只命中一半=0.5944、
   PR 曲线 recall 单调不减）；诊断脚本 `tools/bottleneck*.py` 能定位
   「瓶颈在定位、判类还是排序」—— 本轮迭代的方向就是靠它找出来的，**不是靠试错**。

### 8.2 两条重要的负面结论（也都写进报告）

**负面结论一：单阶段检测器的置信度分支在本数据集上学不出来**

它的**框定位是好的，但「哪个框可信」学不出来**：

| 检查项 | 实测 |
|---|---|
| GT 所属特征点上的框 IoU | **0.742 / 0.757**（定位没问题） |
| 同一框的 obj 分数 | 0.056，在 307 个候选中排**第 135 位** |
| 结果 | 被 top_k 截断淘汰，mAP@0.5 ≈ 0 |
| 根因 | 正样本 2~3 个/图 vs 候选位置 10⁴ 量级（0.3%） |

已尝试并**逐项排除**的方案（均有实测数据）：
改排序方式（obj×cls / 纯 cls / 纯 obj / obj×cls²）· top_k 100→1000 ·
边缘能量当分数 · obj 偏置初始化（-4.5 / -2.0 / 0）· obj 损失正负各自归一化 ·
k-means 定制 anchor · 统一输入尺度 · 检测器候选 + 验证器重打分 ·
按尺寸分档评估（大中小框 mAP **全部为 0**，排除"小目标难检"）·
**把训练跑满**（轮数翻三倍只从 0.0000 升到 0.0007，排除"训练不充分"）

**核心判断**：置信度分支本质是「在上万候选里做二分类、正样本只有 2~3 个」。
本数据集仅 1800 张图、平均每图 2.3 个框，正样本绝对数量太少，学不出可靠置信度
（框回归能学准，因为它是稠密监督；置信度学不准，因为它是极端不平衡的稀疏监督）。

这也正好解释了**为什么滑窗 + 融合方案能工作**：它把同一件事（判断一块区域是不是缺陷）
变成了**稠密监督的分类任务**，不存在正负样本悬殊的问题。

**负面结论二：验证器不能只靠调阈值**

验证器在「GT 框 vs 随机背景」上判别力很强（95.1% vs 26.1%），
但推理时它面对的是**密集重叠的滑窗**，训练时从没见过这种分布，
于是几乎所有覆盖缺陷的窗口都判成缺陷 —— 实测**阈值从 0.5 提到 0.9，
每图框数只从 49.8 降到 48.6**。这条数字是整轮迭代的转折点：
它证明问题不在阈值，必须去改候选质量（加框回归）。

### 8.3 下一步改进建议

1. **换用有预训练权重的主干**：本项目受限于 PaddleDetection 的 numpy<2 依赖无法引入，
   若能单独拿到 backbone 权重，对小数据集帮助会很大；
2. **继续加固精修器**：训练准确率 0.99 / 验证 0.74，过拟合明显。
   注意**不要**靠放宽抖动范围来解决 —— 已实测这样会显著变差（见 §6.0），
   应尝试降低学习率、加强正则或扩充真实候选样本；
3. **继续攻细长缺陷**：加入 0.35 宽高比后 `Sc` 已从 0.092 升到 0.137，
   但 `In 夹杂`（验证集 0.075）与 `Sc` 仍是短板（对比 `PS 麻点` 0.277）。
   可尝试：类别专属的滑窗尺度集合、或对细长缺陷提高输入分辨率后单独跑一遍；
4. **给单阶段检测器加真正有效的机制**：Focal Loss 或 OHEM（只回传损失最大的若干负样本），
   而不是简单调 pos_weight —— 这是让单阶段路线重新可用的唯一现实路径；
5. **数据层面扩充**：把 200×200 原图做重叠裁块，缓解小数据集下正样本过少的问题。

## 九、复现方式

```bash
conda activate paddle_env      # 本机实际路径见第四节

# 1) 训练两个检测网络（串行跑，避免抢显存）
python src/det/train.py --config src/det/configs/yolov3.yml
python src/det/train.py --config src/det/configs/ppyoloe_s.yml

# 2) 训练区域验证器（第二阶段，约 2 分钟）
python src/det/train_verifier.py

# 3) 训练区域精修器（第二阶段升级：判类 + 框回归，约 17 分钟）
python src/det/train_refiner.py --epochs 40 --lr 0.003

# 4) 评估（测试集只在这一步用一次）
python src/det/eval_det.py --model yolov3                          # 单阶段
python src/det/eval_2stage.py --mode window --split test           # 滑窗 + 验证器（初版）
python src/det/eval_fused.py --split test --mode fuse \
    --stride 12 --score-th 0.6 --nms-iou 0.4 --top-k 150 --max-det 50   # 融合方案（最终）

# 5) 迭代诊断工具（找瓶颈用，不是交付流程）
python src/det/tools/bottleneck.py  --split val --limit 100   # 召回上限/判类/排序 拆开看
python src/det/tools/bottleneck2.py --split val --limit 60    # 候选来源与聚合策略对比
python src/det/tools/sweep_refine.py --split val --per-class 20  # 分层抽样超参扫描
python src/det/tools/tune_fused.py  --split val --per-class 25   # 融合后处理精调

# 6) 可视化与 Demo
python src/det/viz_det.py --model yolov3 --split val
python src/det/demo.py --model yolov3 --benchmark

# 7) 汇总结果（生成报告用表格）
python src/det/tools/summarize.py

# 辅助分析
python src/det/tools/kmeans_anchors.py                        # anchor 匹配度分析
python src/det/tools/diagnose.py --model yolov3 --split val   # 诊断 mAP 偏低的环节

# 快速联调（3 个 epoch 验证流程是否通）
python src/det/train.py --config src/det/configs/yolov3.yml --epochs 3 --batch-size 8
```

### 关于测试集

按项目铁律，训练阶段（`train.py` / `train_verifier.py`）**始终只加载 train 与 val**。
测试集仅在最终评估时被读取：`eval_2stage.py --split test`（滑窗与检测器两种模式），
以及验证器在 GT 框上的分类准确率统计。**测试集未参与任何调参决策。**
